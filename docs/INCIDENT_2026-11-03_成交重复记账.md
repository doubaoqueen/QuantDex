# 事故复盘：成交重复记账（2026-11-03）

> 一句话：同一批成交被记了两遍——持仓变 2 倍、现金 −87 万，而**净值只差 1%**，
> 所以它藏了 5 个交易日才被发现。对应决策 D-053（修复）与 D-055（重置）。

## 1. 现象

换手账户（`ledger_topk.sqlite`）在 2026-11-02 的账面：

| 字段 | 账面值 | 应为 | 偏差 |
|---|---|---|---|
| `positions.shares`（49 行） | 257,800 股 | 128,900 股 | **2.000×** |
| `account_snapshot.cash` | −869,765 | 65,118 | −934,882 |
| `account_snapshot.market_value` | 1,889,912 | 944,956 | +944,956 |
| `account_snapshot.total_nav` | 1,020,147 | 1,010,074 | **+1.00%** |
| 权重合计 | 185% | ≈94% | — |

唯一肉眼可见的破绽是**权重合计 185%**（每只票都是真实权重的两倍）。
净值栏因为两处错误互相抵消，看起来完全正常。

## 2. 发现路径

1. 用户质疑"每个策略都在调整所有持仓权重"，要求列否决清单；
2. 列清单时按账户盘点，发现换手账户 `cash = −869,765`（现金账户不可能为负）；
3. 逐只核对 `positions.shares` 与 `trade_log` 成交净额 → 49 只全部恰好 2.00 倍；
4. 反解现金：`1,000,000 − 2 × (934,161 + 254.34 + 467.08) = −869,764.84`，与快照
   **一分不差** → 确认是"同一批成交记了两遍"，不是数据源错误；
5. `git log -S unreconciled_fills` 定位到引入时间，与各账户成交日比对 → 只有成交日
   晚于该提交的账户受影响。

## 3. 根因

`run_pipeline` 里有两条路径都会把成交计入仓位（`src/live/pipeline.py`）：

| 路径 | 代码位置 | 意图 |
|---|---|---|
| ① 本次撮合 | 循环 `fill_results` | 刚成交的单，扣钱加仓 |
| ② 崩溃自愈重放 | `unreconciled_fills(last_snap_date)` | 上次运行若在"撮合后、写快照前"崩溃，靠重放补账（R3-04） |

②的筛选条件是 `fill_date > 上一快照日`。而**今天的成交，fill_date 恰好是今天、
上一快照是昨天**——永远满足条件。于是同一天成交同时被 ① 和 ② 记一遍。

触发条件：**账户已有一个更早的快照，且当天有新成交**——这是每个账户每天都会遇到的
普通情形。

为什么只有换手账户中招：

| 账户 | 首次成交日 | 自愈代码（`a75682a`，10-27 05:35）是否已上线 | 结果 |
|---|---|---|---|
| 大账户 | 10-20 | 否 | 正常 |
| 小账户 | 10-21 | 否 | 正常 |
| 红利账户 | 10-26 | 否 | 正常 |
| **换手账户** | **10-27** | **是** | **2 倍** |

## 4. 为什么净值没崩

```
现金  −934,882（多扣一倍买入成本）
市值  +944,956（多加一倍持仓）
净值  +10,074  ← 恰好等于真实利润，所以"收益率被翻倍"而不是"净值被砍半"
```

显示 +2.01%，真实 +1.01%。**净值看起来健康，是这个 bug 最强的伪装。**

## 5. 修复

- 代码：重放前用本次已撮合的 trade id 去重
  `unre = unre[~unre["id"].isin(done_ids)]`（D-053，提交 `7be1c15`）
- 账户：换手账户重置（D-055）——旧数据导出至 `data/store/_pre_d055/*.parquet`，
  清空四张表后用 `run_pipeline` 重建；新账本 `2026-11-02` 快照 =
  现金 1,000,000 / 市值 0 / 净值 1,000,000，49 笔待成交（942,501 元，成交日 11-03）
- 防线：`run_pipeline` 在记账后若 `cash < 0` 打印告警，提示核对是否有成交被重复记账

## 6. 教训

1. **幂等性没有测试覆盖**：撮合是"写状态"的操作，必须验证"跑两次 == 跑一次"。
   当时有 47 项测试，全是工具函数，没有一项覆盖"同日成交 + 重放"的组合。
2. **防御性代码自己要防御**：自愈重放是为了不丢单，却制造了重复记账。
   凡是"重放/补偿/回放"类逻辑，都必须有明确的"已处理"水位，而不是靠日期推断。
3. **净值是坏指标**：两个相反的错误能互相抵消，让净值曲线看起来完全正常。
   **对账要看组成**（现金、股数、权重合计），不能只看净值。
4. **异常值要当信号**：现金为负、权重合计 185% 都是肉眼可见的异常，
   但它们不在任何监控/巡检里，只能靠人偶然翻到。
5. **发现来自用户的直觉**："为什么每个策略都在调所有持仓权重"——
   一个业务问题，最终查出了记账 bug。
