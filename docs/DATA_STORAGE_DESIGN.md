# 数据存储设计问题分析与改造方案

> 记录于 2026-10-23。触发：行情更新后几百个 parquet 文件被修改，git 历史里出现大量二进制变更。

## 一、一句话病根

**"增量的是行，重写的是文件"**——Parquet 不能原地追加，每次更新都要把整个文件重写一遍；而 git 对二进制文件是"整文件版本"，没有行级 diff。两个"整文件"语义叠加，导致每天追加 1 行 = 重写并提交 8 年历史。

## 二、现状数据

| 指标 | 数值 |
|---|---|
| 日线文件 | 933 个（每个标的 1 个文件，装 2018–2026 全部历史） |
| 平均文件大小 | 133 KB |
| 数据总量 | 121 MB |
| .git 体积 | 148 MB |
| 单次数据更新提交 | 最多 900+ 个 parquet 被修改（实测 e082fa8 = 714 个） |

## 三、为什么这是设计问题（5 个后果）

1. **写放大**：每天更新 1 行 → 重写整个 8 年文件。写放大倍数 ≈ 历史长度 / 增量长度 ≈ 2000 倍。
2. **多设备冲突**：两台机器都更新同一批文件 → 二进制冲突无法 merge，只能整文件覆盖，可能丢数据。
3. **不可审计**：git diff 看不到"今天加了哪一行"，无法 review 数据变化，也无法定位哪次更新引入了脏数据。
4. **仓库膨胀、推送变慢**：每天数百个新 blob；GitHub 单文件 100MB 限制、仓库体积建议上限；clone/push 越来越慢。
5. **代码与数据混在一起**：一次提交既改代码又改数据，回滚时无法分离；破坏"数据可复现"。

## 四、根因拆解

- **Parquet 是 immutable 格式**：没有 append-in-place；`pd.concat(旧, 新).to_parquet()` 必然重写整个文件。
- **git 是内容寻址存储**：二进制文件每次变化都产生新 blob；packfile 的 delta 压缩只能缓解体积，改变不了"文件被修改"的事实。
- **目录布局是"标的分区"**：`daily/{code}.parquet` 把 8 年历史装进一个文件 → 任何一天的数据变化都触碰整个文件。
- **更新流程是"读全量→拼→写全量"**：即使只追加 1 行，也是全量重写。

## 五、正确设计：追加型分区（append-only partition）

核心原则：**每天的数据写到"新文件"里，历史文件永不修改。**

### 方案 A（推荐）：按交易日分区

```
data/store/market/daily_by_date/
├── 2018-01-02.parquet   # 当天全部标的，约 900 行
├── 2018-01-03.parquet
└── 2026-10-21.parquet
```

- 日更 = **新增 1 个文件**（约 100–200KB），0 个旧文件被修改；
- git 真正增量：一次提交只新增 1 个文件，不会出现"几百个文件被改"；
- 冲突几乎不可能：两台设备都只是新增不同日期的文件；
- 可审计：每天新增一个文件，就是当天全部行情，一目了然；
- 读取：用 `pyarrow.dataset` 按 symbol/date 过滤（列裁剪 + 谓词下推），单标的查询依然快；
- 体积：2132 个文件 ≈ 120MB（与现在相当），每年约 25MB，可接受。

### 方案 B：按标的 × 年分区

```
daily/{code}/2026.parquet
```
- 每天仍会改约 900 个"当年文件"（每个文件只含 1/8 数据，写放大降到约 250 倍）；
- **没有解决"几百个文件被修改"的核心问题**，只缓解体积。

### 方案 C：数据不进 git（DVC / 对象存储 / 私有 Release）

- 代码仓库保持小而干净；数据放 DVC remote、S3/OSS、或 GitHub Release 附件；
- 适合数据继续变大、或多设备同步；
- 代价：多一套工具/账号；离线/换机要配置。

### 方案 D：Git LFS

- 数据存 LFS，仓库只存指针；
- 但每天仍会改数百个指针文件（同样有冲突/审计问题），且 LFS 有流量/容量配额；
- **只解决体积，不解决结构问题**。

**推荐组合：方案 A（主存储）+ 方案 C（可选备份/归档）。**

## 六、迁移计划（约半天到一天）

1. **冻结当前数据**：备份 `data/store/market/daily/` 到 `_legacy_per_symbol/`；
2. **一次性生成按日分区**：把 933 个 per-symbol 文件按日期拆分，写入 `daily_by_date/YYYY-MM-DD.parquet`（约 2132 个文件）；
3. **逐行校验**：随机抽样 + 全量对比（行数、close、date、symbol）；
4. **改读路径**：`get_kline` / `build_factor_panel` / 回测脚本改用 `pyarrow.dataset` 读分区；
5. **改写路径**：`update_kline_batch` 只写"当天分区文件"（新文件），不再触碰历史；
6. **提交策略**：数据更新只提交"新增文件"；代码改动单独提交；
7. **保留旧目录**一个版本周期做对照，确认无误后删除；
8. **文档**：更新 README / PROJECT_GUIDE / DECISIONS。

## 七、立刻可做的缓解（不等重构）

- **暂停提交数据更新**：先只提交代码（数据本地/网盘同步）；
- 或把数据放到**独立分支**（如 `data`），代码分支保持干净；
- 备份 `.git` 前先 `git gc`，避免历史继续膨胀；
- 不要在两台设备上同时跑更新（会制造二进制冲突）。

## 八、给非技术视角的一句话

> 你的数据像"每天往一本书里加一页"，但现在的做法是"每天把整本书重新印一遍再存档"——书越厚，每天印的成本越高，而且两个人在同一本书上同时改就会打架。按日分区就是"每天只加一页新纸"，历史那几摞纸永远不动。
