# 公告/新闻信息管线设计：从信息到信号的完整架构（设计稿）

> 状态：**设计稿**（2026-11-14）——P1 获取层待实测源可用性后动工；本文为实施前的架构冻结。
> 关联：TODO 研究待办（研究助手 agent / Alpha101 备粮）、D-068/D-076（预算体检与排期）、D-078（事件纪律）、D-042（FDR 纪律）、blog 第五篇（agent 探针）。
> 一句话定位：**把公告/新闻流变成因子面板里的新列，让它走与量价因子完全相同的闸门与执行机器。**

## 0. 为什么建这条管线（目的性）

- **北极星**（D-068/D-076）：项目最终产品是一个可签字的约束满足方案——"预算 L + 可承受亏损 → 策略选择 + 本金上限 + 校准过的期望带"。11-20 偏差归因校准期望带，之后体检 v2（含 UI）上线。
- 公告/新闻是当前**唯一未接入的信息源族**（BigQuant 对照中"另类数据"差距的合法可补部分）。
- 价值链定位：**信息 → 信号 → 选股**。本文覆盖"信息→信号"（L1~L4，唯一需要新写的部分）；"信号→选股"复用已验证的现有机器（截面 rank → 等权合成 → TopN → T+1 撮合），零改动。

## 1. 信息 → 信号的五步转化链

```
原始公告 ─L3→ 标准化事件 ─L4→ 日频因子列 ─现有机器→ 选股
        （模型打分）   （聚合配方）   （rank→合成→TopN）
```

核心判断：**不需要发明新的选股机制**。公告数据以"第 56 个因子候选"的身份进入现有面板，走与量价因子完全相同的闸门（D-073 三关）、相同的执行链、相同的影子盘对照。唯一需要新写的是 L3（模型打分）与 L4（事件聚合），合计一个脚本 + 一个聚合函数。

## 2. 五层架构（模型含量是设计关键）

| 层 | 职责 | 模型含量 | 产出 |
|---|---|---|---|
| **L1 获取层** | 公告/新闻入库：巨潮/东财公告接口、财联社电报等（源可用性实测后定） | 无（纯代码） | 原始文本流 {date, symbol, title, body, source} |
| **L2 清洗层** | 哈希去重、软文黑名单、symbol 对齐、元数据补全 | 无（纯代码） | 干净事件流 |
| **L3 消化层** | 文本 → 结构化 JSON | ★**qwen3:8b 本地推理（唯一模型层）** | {event_type, polarity, horizon_days, confidence} |
| **L4 特征层** | 事件流 → 日频因子行（§3 四种配方） | 无（纯代码） | 面板新列 signal_* |
| **L5 入模** | 拼接进因子面板 → 打分/策略 → 闸门 → 影子盘对照 | 无 | 与量价因子同一条执行链 |

## 3. L4 聚合配方：信号诞生的四种标准形态

公告是**不规则事件流**，面板是**日频矩阵**，中间必须聚合。四种配方（全部有文献先例）：

| 配方 | 公式形态 | 信号含义 | 适合 |
|---|---|---|---|
| ① 事件哑变量 | 过去 N 天内有该类公告 = 1 | 类别型：当前处于"事件期" | 稀少而重大（回购/重组） |
| ② 强度聚合 | 过去 N 天情绪得分均值/求和 | 连续型：近期整体口风 | 新闻流 |
| ③ 衰减加权 | Σ polarityᵢ × exp(−Δtᵢ/τ) | 旧信号衰减、新事件主导 | 公告漂移（PEAD） |
| ④ 计数异常 | 公告数量相对自身历史的 z-score | 信息流异常（有事要发生） | 前兆检测 |

**参数纪律（rev_5 教训的新闻版）**：衰减窗口 τ 必须匹配持有期——调仓 20 日 → τ 取 10~20 日；取 3 日等于把 3 日预测力挂 20 日持有 = 掺噪音（第四篇已付过学费）。

## 4. 三个入口（信号 → 选股的接入方式）

| 入口 | 机制 | 性质 | 纪律 |
|---|---|---|---|
| A. 加入现行打分 | 事件列作为第 4+ 因子 → 截面 rank → 等权合成 → TopN | 主流：让现有策略"看到"事件 | D-073 三关 + 与现有因子正交化 |
| B. 独立事件策略 | 每日扫描"今日新回购/预告"→ 事件组合 | 新策略账户（图谱事件驱动型） | 完整 WF + 归因 + 成本复核 |
| C. agent 查询层 | 不进打分，人工参考 | 信息展示，零信号主张 | 绝不冒充信号 |

**先 A 后 B**：A 改动小、闸门现成；B 是新账户要完整验证。C 是 agent 的展示位。

## 5. 第 0 步：信号存在性验证先行（管线动工前）

- 做法：拉 2018~2026 全部回购/业绩预告公告 → 事件后 1/5/10/20 日超额收益分布（PEAD 式统计）。
- 判定：事件后超额 ≈ 0 → 信号不存在，**管线不建**；显著 → 才进入 P1。
- 成本：半天，不需要管线——只需巨潮历史公告 + 现有收益面板。**先证明答案存在，再让 AI 做题。**

## 6. 多重检验爆炸风险（D-042 事件版，本管线最大科学风险）

事件类型（回购/减持/业绩/合同/诉讼…≈10）× 聚合窗口（5/10/20/60）× 衰减形态（哑变量/线性/指数）≈ **上百个隐式假设**——D-042 教训（46 因子 FDR 后 0 通过）在此会加倍适用。纪律：

1. **每种事件类型只测一个预设假设**（回购→利好→20 日窗），禁止扫参数空间；
2. 扫描产生的"显著"一律按 D-042 存疑（不作为准入证据）；
3. 全部候选过 FDR 后才能谈准入；样本外（影子盘）是终审。

## 7. 分阶段实施（对接主排期）

| 阶段 | 内容 | 工作量 | 前置 |
|---|---|---|---|
| **P0 信号存在性** | 回购/预告事件后收益统计（§5） | 半天 | 无（随时可开工） |
| **P1 管线核心** | L1 获取（先公告）+ L3 打分器 + L4 聚合 + news 存储 | 1~2 天 | P0 通过 |
| **P2 闸门验证** | 事件因子 RankIC + 正交化 + FDR | 半天 | P1 有数据 |
| **P3 agent 查询层** | 50 行循环 + 5 工具（get_announcements/get_news/get_factor_snapshot/resolve_symbol/get_ledger_summary） | 1 天 | P1 |
| **P4 RAG 知识层** | D 日志/研报向量化 → 助手回答"为什么否决断路器" | 1 天 | P3 |
| **体检 v2（主线）** | D-076 UI：输入 L → 输出策略+金额+校准期望带 | — | **11-20 归因（硬节点）** |

排期纪律：**全部排在 11-20 归因之后**（秤没校准前不加砝码）；唯一例外是 P0（半天纯研究，可提前验证方向）。

## 8. Agent 岗位边界（两个岗位，明确不做清单）

**岗位一：批量打分器（主力，非 agent）**——固定 prompt + JSON schema + temperature 0，逐条消化。失败三级降级：JSON 解析失败重试 1 次 → 降级词典规则 → 标记人工待审（audit.py 对账纪律）。

**岗位二：研究助手（agent）**——受限工具集 5 个（get_announcements / get_news / get_factor_snapshot / resolve_symbol / get_ledger_summary）+ 50 行循环 + 熔断。用途：自然语言查数据、标注辅助预筛。

**明确不做**：自由联网搜索（另立决策）、自动写文件/下单（副作用）、多智能体协作、记忆体长期演化、付费数据爬取（ToS 黄灯，2026-11-15 已标注）。

## 9. 模型选型与成本账本

- **模型**：qwen3:8b（Ollama 0.32.15，RTX 5070 12GB 全进显存，实测 110 tok/s）；14B Q4（9GB）为推理升级档。
- **吞吐**：949 只 × 日均 ~2 条公告 × ~400 token ≈ 76 万 token/天 → 约 2 小时/天，收盘后批量跑。公告类（每天量小）远低于此。
- **幻觉防线**：固定 JSON schema + 字段枚举约束 + 每轮抽检对账（audit 纪律）+ 三级降级。qwen3 思考模式吃 token 预算（博客第五篇教训），打分 prompt 用 `/no_think`。
- **打分纪律**：模型只出现在"文本→结构化"一步；**回答中的数字必须来自工具/原文**（探针铁律③）。

## 11. 风险与边界

1. **多重检验爆炸**（§6）——本管线最大的科学风险，纪律高于灵感。
2. **另类数据脏度**：软文/广告/重复推送——L2 去重 + 抽检；股吧类慎用。
3. **持有期错配**：公告快信息定价分钟级，T+1 开盘追不上——只取慢信息（公告漂移）与周级聚合。
4. **数据授权**：不采 BigQuant 试用 SDK 批量拉数据（ToS 黄灯）；历史公告走公开接口自建。
5. **换手成本**：事件因子若衰减快会推高换手——τ 匹配纪律（§3）+ 影子盘实测复核。

## 12. 开发顺序建议

```
P0 信号存在性（半天，可提前） → [11-20 归因，硬节点] → P1 管线核心（1~2 天）
→ P2 闸门验证（半天）→ P3 agent 查询层（1 天）→ P4 RAG（1 天）
→ 与 LightGBM 基线合流（事件因子进特征池）
```

每阶段完成即提交并更新 TODO；P0 的结果决定 P1 是否开工——**信号不存在，管线不建，这条纪律同样适用于本设计文档自己。**
