# 第七篇：两千行文件的结构手术——AI 协作里的"形状债"

项目代号：QuantDex｜纯学习向项目，不构成任何投资建议

导读：前几篇讲的都是"数字对不对"，这一篇讲"代码长什么样"。起因很简单：我在控制台代码里看到一段三十多个分支的 if 链——连我这个基础程序水平的"小手子"都看得出这写得很烂。有意思的是，这个项目经历了十几轮 AI 迭代、好几轮深度审查，居然没有一轮发现它。这一篇把结构手术记录下来：什么是典型的"形状债"、手术前后差在哪（带实测数字）、以及怎么让它以后长不出来。

## 一、为什么十几轮审查都没看见它

先认账：就在几天前我做了一轮全仓深读审查，报告写了十几页——照样没标出那段 if 链。最后是我自己翻代码时看到的。这不是审查不够努力，而是三个机制性的原因：

1. **所有审查都是语义审查**。查口径、查前视、查账本、查安全——这些只看"行为对不对"，而分发结构不改变行为输出，行为等价的审查天然看不见它。测试也一样：它们断言的是净值和状态码，不是代码的形状。
2. **AI 迭代从不领"结构"任务**。每一轮的任务都是"加端点 X""修 bug Y"，没人下过"重排这个文件"的任务。而 AI 有很强的复刻周边代码的倾向——if 链只会吸引更多 if 链。每次局部改动都是对的，全局形状慢慢烂掉。这大概是 AI 协作最典型的失败模式：**局部正确 ≠ 全局健康**。
3. **形状没有执法者**。测试守行为，lint 守风格和 bug 类，复杂度没有任何一层在管。

所以解法不是"下次审查更仔细"，而是给形状装上执法者。文末讲。

## 二、先回答一个质疑：if 链到底影不影响行为？

我此前说"if 链不改变行为"——这话不严谨，值得掰开。行为有两本账：

**输出等价性**：分发方式不改变任何一次请求的处理结果——这是"行为保持重构"的本意。

**代价账**：你说的 O(N) 是真的。实测（26 个路由、96% 命中率的混合流量）：

| 分发方式 | 26 个路由 | 260 个路由 | 增长特性 |
|---|---|---|---|
| if 链（逐段比较） | 241 ns/次 | 1832 ns/次 | **线性 O(N)** |
| 字典路由表 | 48 ns/次 | 46 ns/次 | 平坦 O(1) |

量级语境：本系统一次 `/api/overview`（SQLite + pandas）约 2ms，26 路由的 if 链占其 **0.012%**——在这里是零头的零头，性能不是重构的动机。但同样的结构放进两个场景就是实打实的问题：**路由数继续增长**（每加一个端点，所有请求都变慢一点），或者**放进热循环**（回测里逐日逐标的的分发，一天几十万次）。

所以我修正后的表述是：**if 链的代价主要记在形状账上（人每次读 O(N)，AI 每次复刻 O(N)，而且只增不减），性能账在 N 大或频率高时从隐形变主导**。你的方向感是对的——只是在本系统的 webapp 里，性能账暂时还是零头。

## 三、手术记录：五个典型病灶（前后对比）

### 病灶 1：30 段 if 分发 → 路由表

**前**（do_GET 的分发段，26 个 GET 端点各占 2-3 行）：

```python
if u.path == "/api/overview":
    return self._send(200, overview(q.get("account", ["large"])[0]))
if u.path == "/api/nav_history":
    return self._send(200, nav_history(q.get("account", ["large"])[0]))
if u.path == "/api/trades":
    return self._send(200, trades(q.get("account", ["large"])[0],
                                   q.get("limit", ["30"])[0]))
# ……还有 23 段
```

**后**（声明式路由表 + 参数助手）：

```python
_GET_ROUTES: dict = {
    "/api/overview":   lambda q: overview(_acc(q)),
    "/api/nav_history": lambda q: nav_history(_acc(q)),
    "/api/trades":      lambda q: trades(_acc(q), _qparam(q, "limit", "30", cast=int)),
    # 加端点 = 这里一行 + 一个函数，不再碰分发器
}

# do_GET 里只剩三行：
handler = _GET_ROUTES.get(u.path)
if handler is None:
    return self._send(404, {"err": "not found"})
return self._send(200, handler(parse_qs(u.query)))
```

收益三层：`q.get("account", ["large"])[0]` 重复 20+ 遍收敛为 `_acc`；垃圾参数（`?limit=abc`）从 **500 崩成 400**（`_qparam` 的 cast 失败抛 `_BadParam`）；分发 O(N)→O(1) 是免费副产品。

### 病灶 2：永远走不到的优雅分支

三个下单处理器里都写了"账户不存在"的优雅返回，但底层取连接的代码是：

```python
def _db(acc):
    p = ACCOUNTS[acc]["db"]      # 账户名拼错 → KeyError → HTTP 500
    ...
```

只有"账户存在但账本文件缺失"才能走到那句优雅分支；账户名拼错反而 500。改 `.get(acc)` 一行，优雅分支活了。这个 bug 是新写的 HTTP 冒烟测试当场抓出来的——**特征测试先行不是仪式，是排雷**。

### 病灶 3：上帝函数 run_pipeline（本次最大的一台手术）

拆解前：**1 个函数，412 行，272 条语句，77 个分支，mccabe 复杂度 68**——撮合、自愈重放、状态应用、净值计算、下单、快照落库、缺口回填、日报组装八件事挤在一起，全仓审计（AST 扫描）确认是最差点。

拆解后（阶段函数 + 编排主干）：

```python
def run_pipeline(...) -> dict:
    # 1) 撮合到期订单（T+1 开盘价）
    fill_results = _match_pending_orders(store, led, latest, dry_run)
    # 2) 账户状态 + 应用撮合结果 + 自愈重放（D-053/D-062）
    cash, new_shares, snap_now, last_snap_date = _apply_state(...)
    # 3) 最新收盘价与净值
    mv, nav_now, prices_close = _account_nav(...)
    # 4) 下单（调仓日或首次建仓；已有 pending 时不再重复下单）
    bootstrap, held_days, cadence_ok, scheduled, rebalance_day = _rebalance_decision(...)
    _submit_orders(...)
    # 5) 持仓表 + 快照 + 日报
    positions, pos_rows = _build_positions(...)
    cum_cost, check_lines, check_ok, pending_after = _persist_day(...)
    report, report_path, ... = _daily_report(...)
    # 推送 + 返回
```

| 指标 | 拆解前 | 拆解后 |
|---|---|---|
| run_pipeline 复杂度 (mccabe) | **68** | **11** |
| 语句数 | 272 | 46 |
| 分支数 | 77 | 9 |
| 文件全量 lint | 2 项 | **0 项**（含清掉两条预存项） |
| 全量测试 | — | 110/0 通过 |

拆解时还顺带抓出两个潜伏雷：① 日历缺失时 `orders` 变量未赋值即引用（NameError，只是触发条件罕见）；② `今日盈亏` 这类显示值如果用"从收益率反推"的花哨写法会有浮点 ulp 级风险——**拆解时严格逐行搬运、显式传参，才能让这类雷现形**。

### 病灶 4：静默 fallback

策略分发原本是 if/elif/else——else 意味着任何拼错的策略名都会静默跑成 corrected，产物还落在 corrected 的文件名下。这正是 D-106 事故的同款（CLI 参数填错 → 错口径产物）。改成字典表 + 未知策略硬报错：

```python
_STRATEGY_BUILDERS = {"corrected": ..., "dividend": ..., "topkdrop": ...}
builder = _STRATEGY_BUILDERS.get(strategy)
if builder is None:
    raise SystemExit(f"未知策略名 {strategy!r}——拒绝静默 fallback")
```

本仓库的教训已经两次证明：**静默 fallback 是口径事故的放大器**（D-106 红利重跑误填参数跑成 corrected；D-106 后 05/06 号加了守卫，这次轮到 pipeline）。

### 病灶 5：三个小件

- **缓存主本出门**：`store.read` 缓存命中返回同一个 DataFrame 实例，调用方就地加一列 → 缓存被污染，同进程下次读到脏对象。改返回副本。
- **费率字面量**：webapp 人工下单的佣金/印花/过户/滑点全是字面量，config 改了不传导（pipeline.py 的注释里就记录过同款事故）。收编 config。
- **非原子写**：按日分区直接写目标路径，进程中断留半截 parquet。改 tmp + `os.replace`（与注册表的 D-059 同款）。

## 四、手术怎么做才不流血

这次是钱路径（天天在跑的影子盘流水线），流程值得记录成纪律——已写进 CODE_STANDARD §10：

1. **独立成轮**：只动结构不动行为的重构不与功能/修 bug 混批；
2. **特征测试先行**：动刀前确认已有端到端测试罩住（webapp 有真实 Server 冒烟，pipeline 有真实库 + 邮件去重幂等测试）；
3. **逐行搬运**：阶段函数只做"移动 + 显式传参"，禁止顺手优化——拆解时我曾想把 `今日盈亏` 写得"更聪明"，立刻退回去逐行搬；
4. **机械 diff 核对**：webapp 用端点集合比对（26 GET + 5 POST 零缺失零多余）；
5. **全量测试收口**：110/0；
6. **棘轮兑现**：ruff.toml 里 pipeline.py 的复杂度豁免白名单**按约删除**——豁免清单只许减不许增。

## 五、怎么让它以后长不出来

三道防线（都已就位）：

1. **机械执法**：ruff 加 `C901`（复杂度 ≤25）/`PLR0912`（分支 ≤20）/`PLR0915`（语句 ≤90），阈值钉在现存最差之下——新代码超线立刻报错。存量债务进白名单，改一个删一个。
2. **命名模式**：分发用表、常量单源、写仓过锁、缓存不出门、函数预算、文件预算——把模式命名写进 CODE_STANDARD，以后每次让 AI 改代码规则随上下文生效，不依赖 AI 自觉。
3. **专项结构轮**：AI 不会主动重构是对的——这类轮次要显式派任务，而有了棘轮和铁律，什么时候该派、派给谁，数据自己会说话。
