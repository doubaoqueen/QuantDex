# 第五篇：给本地 7B 发一套工具，它真的会查——agent 落地实测

项目代号：QuantDex｜纯学习向项目，不构成任何投资建议

导读：这一篇回答一个我憋了很久的问题：本地跑的 7B 小模型，能不能当 agent 的"大脑"——我说一句话，它自己查数据、自己汇总？这篇的全部价值在于一张**前后对照表**：同一句话，裸模型答什么、发一套工具之后答什么。差别大到不像同一个模型。

## 一、起点：一个错误的认识

我一直以为"联网查询、查数据"是云端模型的专属能力，本地模型只能离线聊天。认知修正从一句大白话开始：**模型从来不需要联网，需要联网的是工具。** 模型只负责"决定调哪个工具、填什么参数、怎么解读结果"，HTTP 请求由工具代码发出——akshare 从东财接口拉数据，和浏览器拉网页没有本质区别。

验证分三步：① 盘点硬件能不能养活本地模型；② 实测 tool calling 通不通；③ 7 个场景的落地测试，并留下探针使用前后的完整对照（本篇核心，见第四节）。

## 二、地基盘点：这张卡能养活什么

先清理：Ollama 里 5 个模型躺了 5 个月，删掉 4 个。实测 RTX 5070 12GB：7B 的 Q4 量化版（4.7GB）**100% 进显存**，生成速度 110 tok/s，热运行 2.6 秒出一段 200 字回答；新闻打分一次通过（回购公告 → `{"polarity":"利好","event_type":"回购"}`，JSON 零差错）。

一个显存租赁常识：这张卡上还住着另一个项目的 Qwen3-VL 服务（vLLM，占 9.7GB）——**Ollama 的 4.7GB 和它装不下同一张卡**。模型是租户，用谁开谁。顺带把 WSL 那个服务的启动参数也实测修正了（0.88 → 0.86，桌面基线显存涨了，旧档位起不来——**任何"占 9.6GB"的承诺都要用当天的实测背书**）。

## 三、翻车两轮：一次怪数据源，一次怪我自己

搭好 50 行 agent 循环 + 3 个封装工具（akshare 真数据），第一轮 7 场景大面积失败。排查发现**两层问题叠在一起**：

- **数据源层**：akshare 的新闻接口死于 py_mini_racer 的 JS 正则（和此前禁用新浪降级同族），行情接口死于东财断连（就是控制台日志里连续出现的那一个）。十个工具九个坏，模型还没被测到就被脏工具拖下了水。
- **我自己的探针**：重写第二版时把发往 API 的 `tools` 参数弄丢了——模型从头到尾**没收到工具定义**，它就开始"表演调用工具"："工具返回结果为：中国平安权重 5.51%……"，一份看起来完全合理、**纯属编造**的权重表。修一行代码，同一请求重跑 10 次，工具触发 10/10。

**教训一：怀疑结论之前，先怀疑测量仪器；教训二：模型没收到工具时不会说"我没有工具"，它会顺着话头表演。** agent 循环必须把"工具列表确实发出了"当成循环代码的责任。

## 四、探针使用前后：同一句话，两种回答

下面是修好仪器后的实测原文（模型 qwen3:8b，原样摘录，未修饰）。

**问题 1：** `沪深300 权重最高的前 5 只成分股是哪些？给代码和权重`

**探针前（裸模型）**——它先思考了 700 字，甚至自己承认了数据是旧的：

> 思考摘录："通常，这些数据由中证指数有限公司维护，但可能没有公开的实时数据。所以可能需要参考第三方数据源或者历史数据。"
>
> 正文："以下是基于**2023年12月**的最新数据（可能因市场波动略有变化）……贵州茅台 600519 权重 4.98%、中国平安 601318 权重 4.85%、招商银行 600036 权重 4.65%……"

**探针后（agent + 工具）**——调用 `get_index_top_weight`，返回当日中证指数公司真实数据：

> 1. **600519 贵州茅台** - 权重 3.836%
> 2. **300308 中际旭创** - 权重 2.719%
> 3. **300750 宁德时代** - 权重 2.716%
> 4. **601318 中国平安** - 权重 2.481%
> 5. **600036 招商银行** - 权重 2.376%

对比要点：裸模型的每个数字都是错的，**而且两年前根本不在前排的中际旭创、宁德时代整个缺席**——它不知道自己缺什么。更微妙的是那句"可能因市场波动略有变化"：**加免责声明的编造，还是编造。** 而它思考里明明写过"可能没有公开的实时数据"——它知道，但依然把旧数字当答案递出来了。

**问题 2：** `中际旭创最近 5 个交易日的收盘价是多少？`

**探针前（裸模型）**——两处硬伤：

> "中际旭创（股票代码：**300567**）……截至我知识更新的时间（2023年10月），我无法提供实时或最新的股票收盘价数据。要获取……您可以通过同花顺、东方财富、雪球……"

代码记错了（真实是 300308），然后给了一份"去哪查"的指南——礼貌、正确、毫无用处。

**探针后（agent + 工具）**——先正确解析出 300308，再调 `get_kline_recent` 返回当日真实收盘价：

> 中际旭创（300308）最近5个交易日收盘价如下：2026-11-09：452.03元 … 2026-11-13：466.20元（前复权）

**这张对照表就是 agent 的全部价值**：裸模型的失败不是"能力不够"，而是**结构上无路可走**——没有工具，它只能用冻结的训练记忆填空，填错了还要体面。给一套工具之后，"我知道我不知道"变成了"我去查"。

## 五、判定数据：7 场景 A/B（qwen2.5:7b vs qwen3:8b）

| 场景 | qwen2.5:7b | qwen3:8b |
|---|---|---|
| S1 单工具+参数 | ✅ | ✅ |
| S2 本地行情+解读 | ✅ | ✅ 表格更规整 |
| **S3 两步链**（权重第一→查它行情） | ❌ **没查权重表，凭记忆猜了 600000** | ✅ 先查权重表→再查行情，两步完整 |
| **S4 名称→代码** | ❌ 中际旭创记成 300533 | ✅ 正确解析 300308 |
| S5 幻觉抗性（菜单外问题） | ✅ 不编造 | ✅ 且回答更干脆 |
| S6 错误处理（无效代码） | ✅ | ✅ 带诊断建议 |
| S7 超出工具范围 | ✅ 诚实拒绝 | ⚠️ 空回答* |

*qwen3 默认带思考模式，思考 token 会吃掉输出预算——S7 的空回答就是预算被思考耗尽所致，调大 `num_predict` 或关闭思考即解。这也是本轮唯一的意外收获：**思考模型要为思考付 token 账单**。

两个失败场景（qwen2.5 的 S3/S4）是同一类病：**让模型凭"参数记忆"填实体**。它对"中际旭创的代码"毫无把握，但不会承认——会给你一个自信的错答案。qwen3:8b 在 S3 展示了正确的两步链，这就是"新一代"的真实差距：不在文采，在锚定。

## 六、三条工程铁律

1. **工具菜单必须窄。** akshare 有 1000+ 接口，全暴露给 7B 等于开卷考试还允许编答案。只封装 3-5 个项目真用的工具，参数 schema 写死。
2. **错误熔断放循环层。** 模型遇到工具报错会固执地用相同参数重试 6 次。循环里判断：同参数失败过一次，注入"禁止重试"——它立刻改道或如实报告。
3. **实体解析走工具。** 见 S3/S4。规则一句话："使用标的代码前必须先用工具查询，禁止凭记忆填写。"

另有一条/qwen3 专属：**思考模型要为思考付 token 账单**——`num_predict` 必须把思考算进去，或者用 `/no_think` 关掉。

这次验证让我兴奋了一晚上（真的跑通了！），但兴奋不能绕过自己的闸门。agent 在 QuantDex 里的真实岗位是**新闻/公告管线的取数层**——而那条管线的前置（数据源选型、公告因子验证）还没开工；关键路径上还站着 11 月 20 日的影子盘四周归因。所以决定：**agent 排进 TODO，排在新闻管线之后**，探针脚本存档在 `docs/blog/attachments/agent_probe.py`，开工时直接改造。兴奋的正确打开方式是排期，不是加班。

## 八、核心代码

agent 循环的全部（工具注册 + 熔断 + 多轮），完整可运行版见 `docs/blog/attachments/agent_probe.py`：

```python
# ---- 工具注册：菜单只有 3 个，schema 写死 ----
TOOLS = [
    {"type": "function", "function": {"name": "get_stock_news",
        "description": "获取某只 A 股个股的近期新闻列表",
        "parameters": {"type": "object", "properties": {
            "symbol": {"type": "string", "description": "6 位股票代码"}},
            "required": ["symbol"]}}},
    # ... get_quote / get_index_top_weight 同构，略
]

def run_tool(name, args):
    fn = DISPATCH.get(name)                      # DISPATCH = {'get_stock_news': t_news, ...}
    if fn is None:
        return {"error": f"未知工具 {name}"}      # 菜单外调用直接拒
    try:
        return fn(**args)
    except Exception as e:
        return {"error": str(e)[:200]}           # 错误也回填给模型，让它自己决定下一步

# ---- agent 循环：模型吐 tool_call → 执行 → 结果回填 → 再来 ----
def agent(query, max_iters=6):
    msgs = [{"role": "user", "content": RULES + "\n\n" + query}]
    fail_sig = {}                                # 熔断：同参数失败过一次就禁重试
    for _ in range(max_iters):
        m = chat(msgs)                           # POST /api/chat，带 tools=TOOLS
        if not m.get("tool_calls"):
            return m.get("content")              # 模型认为信息够了 → 最终回答
        msgs.append(m)
        for call in m["tool_calls"]:
            fn, args = call["function"]["name"], call["function"]["arguments"]
            sig = json.dumps([fn, args], sort_keys=True)
            result = ({"error": "该调用已失败一次，禁止重试"}
                      if fail_sig.get(sig) else run_tool(fn, args))
            fail_sig[sig] = 1
            msgs.append({"role": "tool", "content": json.dumps(result, ensure_ascii=False)})
```

就这些。没有框架、没有 LangChain——一个 while 循环加一个字典。

## 九、收个尾

这一篇没有产生任何收益：agent 排期在后面，模型还有小瑕疵，新闻管线八字没一撇。它产生的是**确定性**——本地模型 + 工具调用这条路的每一步坑（仪器污染、表演式调用、参数记忆幻觉、思考吃预算、显存租赁），都已经被我踩过并记下了。等排期轮到它时，不用再摸黑。

**裸模型知道自己是旧的，还是把旧答案递了出来；agent 不知道未来，但它知道去哪查。这大概就是这一篇全部的结论。**
